# Контекст проекта и каретки в промпте модели: спецификация `flc-context/v1.1`

Статус: v1.1, 2026-10-09. Учтено ревью `docs/CONTEXT_SPEC_REVIEW-RU.md` (номера находок указаны в скобках, например [A1]).
Общая для C# и Go. Обязательные правила сформулированы так, чтобы обучение и плагин собирали **побайтно одинаковый** промпт;
всё, что может отличаться (содержимое фактов), отделено и проверяется эталонами (раздел 11).

## 1. Что меняется и что нет

**Не меняется:** рантайм плагина (`ml-core`, `.cml`, нативные ядра), архитектура сети, токенизаторы `cs-16384.bpe` /
`go-16384.bpe`, жадная генерация, лечение токена (`healedBoundary`, `healMode` как сейчас), порог показа по `confProd`,
защита от повторов, обрезка закрывающих символов.

**Меняется только сборка промпта.** К SPM-промпту добавляются два необязательных куска:
1. **Профиль проекта** — внешние библиотеки проекта (Serilog или стандартный `ILogger`, zerolog или `slog`, xunit или NUnit…).
2. **Блок фактов у каретки** — что видно в точке редактирования.

Оба необязательны: модель обучается и с ними, и без них (раздел 10), плагин подаёт то, что смог посчитать.

## 2. Промпт целиком

Обозначения: `encode` — `BpeTokenizer.encodeBytes` токенизатора модели; `[X]` — id специального токена `X`, вставленный
напрямую (`specialId`), а не текстом. Текст документа — как в редакторе IntelliJ: **без BOM, переводы строк `\n`** [A4]
(в обучающих данных CRLF и одиночные CR приводятся к `\n`, BOM отбрасывается).

```
[<|fim_prefix|>] [<|fim_suffix|>] encode(суффикс) [<|fim_middle|>]
  ( [<|reserved_0|>] encode(профиль) )?                       ← раздел 4
  [<|file_sep|>] encode(путь + "\n")
  encode(P[0:I])
  ( [<|reserved_1|>] encode(факты) [<|reserved_2|>] )?        ← раздел 5
  encode(P[I:])
```

- `суффикс` — текст после конца текущей строки, первые `promptSuffixTokens` токенов (как сейчас: `InlinePrompt.spm`).
- `P` — текст префикса: от начала окна (`stableTail`, раздел 6) до **лечёной границы** (как сейчас); набранный остаток после
  границы по-прежнему ограничивает генерацию.
- **Точка вставки `I`** [A1]: начало **последнего пре-токена `go-code-1` в `P`, который начинается с `\r` или `\n`** — это
  перевод строки перед текущей строкой вместе со всеми пустыми строками над ней и отступом текущей строки
  (`(\r\n|\n|\r)+[ \t]*` одним пре-токеном). Если такого пре-токена в `P` нет (первая строка файла, или окно начинается внутри
  текущей строки — очень длинная строка [G2]), `I = 0`: блок стоит сразу после заголовка.
- Если лечёная граница стоит не позже начала текущей строки (каретка в отступе), `I = |P|`: блок в самом конце промпта [A2].
- С таким `I` верно `encode(P[0:I]) + encode(P[I:]) == encode(P)`, поэтому токены текущей строки и все правила движка
  (лечение, стоп, повторы) работают как без блока. Это обязательный тест (раздел 11).
- Нет профиля — нет `[<|reserved_0|>]` и текста профиля. Нет фактов — нет `[<|reserved_1|>]…[<|reserved_2|>]`. Пустых блоков
  не бывает.

### Пример (C#), каретка после `_logger.`; иллюстрация, точные эталоны — раздел 11

```
<|fim_prefix|><|fim_suffix|>
        await _orderRepository.UnitOfWork.SaveEntitiesAsync(cancellationToken);
        return true;
    }
}<|fim_middle|><|reserved_0|>MediatR Microsoft.Extensions.Logging FluentValidation<|file_sep|>src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs
using MediatR;
…
        var order = new Order(request.UserId, request.UserName, address);<|reserved_1|>RET Task<bool>
ARG request:CreateOrderCommand cancellationToken:CancellationToken
LOCAL address:Address order:Order
FIELD _orderRepository:IOrderRepository _logger:ILogger<CreateOrderCommandHandler>

MEMBER BeginScope<TState>(TState state)->IDisposable; LogInformation(string message, params object[] args)->void +3; …<|reserved_2|>
        _logger.
```
Генерация: `LogInformation("Creating order {OrderId}", order.Id);`, затем стоп-токен.

## 3. Служебные токены

| Токен | Значение |
|---|---|
| `<|reserved_0|>` | начало профиля проекта; профиль заканчивается следующим `<|file_sep|>` |
| `<|reserved_1|>` | начало блока фактов |
| `<|reserved_2|>` | конец блока фактов |
| `<|reserved_3|>` … `<|reserved_8|>` | свободны |

- Вставляются только по id, никогда не получаются из текста.
- **Никогда не являются целью обучения** [A3]: loss на них и на позициях, предсказывающих их, маскируется (раздел 10).
  Иначе модель научится ставить `<|reserved_1|>` в конце строки, вероятность стопа разделится, и `confProd` поедет.
- В нынешних моделях (`cs/go-nn-31m/50m`) эти токены не обучались: формат `v1.1` годится только для моделей, обученных на нём [G5].

## 4. Профиль проекта

**Текст:** корни библиотек через пробел, без слова `DEPS` [G1]: `MediatR Microsoft.Extensions.Logging FluentValidation`.

**Порядок и лимит:** по убыванию числа файлов, где корень встречается, при равенстве — по имени; корни добавляются, пока
`len(encode(join(корни, " "))) ≤ contextDepsMaxTokens` (48) [B3]. Символьного лимита нет.

**Какие файлы считаются [E2]:** исходники проекта (C# — репозиторий/решение, Go — модуль) без `bin/`, `obj/`, `vendor/` и
сгенерированных файлов (те же шаблоны, что `discovery.generated_patterns`: `*.g.cs`, `*.Designer.cs`, миграции и т. п.).
**Кроме текущего файла.** Корень попадает в профиль, если встречается минимум в **2 других** файлах. Implicit usings SDK,
`<Using Include>` из csproj и `global using` из сгенерированных файлов **не учитываются** (в обучающих данных их нет).

**C#:** `using X;` / `global using X;` / `using static X;` / `using A = X;` в исходнике. Отбрасываются `System`, `System.*` и
пространства имён самого проекта: объявленные в нём (`namespace …`) и их вложенные (`ns == d` или `ns` начинается с `d.`) [E3].
Корень: `Microsoft.Extensions.*`, `Microsoft.AspNetCore.*` → три сегмента; остальные `Microsoft.*`, `Google.*`, `Amazon.*`,
`Azure.*` → два; всё остальное → первый сегмент.

**Go:** пути импорта. Отбрасываются стандартная библиотека (первый элемент без точки) и пакеты самого модуля (путь модуля:
в плагине — из `go.mod`; в обучающих данных `go.mod` нет, используется эвристика `scripts/deps_profile.py`, расхождение на
vanity-путях и многомодульных репозиториях допускается [E3]). Корень: `github.com|gitlab.com|bitbucket.org|golang.org/x` →
три элемента, остальные хосты → два, суффикс `/vN` отбрасывается.

**В плагине [E1]:** счётчики корней кэшируются на проект по **проиндексированному** состоянию файлов; корни текущего файла
вычитаются по его проиндексированному состоянию. Правка импортов в текущем файле до переиндексации профиль не меняет (иначе
профиль менялся бы при наборе `using`).

**Место:** между `<|fim_middle|>` и `<|file_sep|>` [B3]. Профиль стоит после суффикса, поэтому пересчитывается при каждом
холодном prefill; это ≤ 48 токенов.

**Во всех видах документов [C2]:** plain — `[<|reserved_0|>]профиль[<|file_sep|>]путь\n…`; PSM — `[<|fim_prefix|>][<|reserved_0|>]профиль[<|file_sep|>]…`;
SPM — как в разделе 2.

## 5. Блок фактов

### 5.1. Строки (`v1.1`)

Каждая строка: ключ, пробел, элементы. Строки внутри блока разделяются `\n`; после последней — сразу `[<|reserved_2|>]`.
Порядок вывода — как в таблице. Пустые строки не выводятся.

| Ключ | Что | Формат элементов | C# | Go |
|---|---|---|---|---|
| `RET` | тип результата охватывающей функции/метода/лямбды | один тип | да | да |
| `EXPECT` | ожидаемый тип у каретки — только однозначный (аргумент с единственным типом параметра, `return`, присваивание, инициализатор, условие `if`/`while` → `bool`) | один тип | да | да |
| `ARG` | параметры в области видимости (метод, лямбда, primary-конструктор; в Go и получатель метода) | `имя:тип` через пробел | да | да |
| `LOCAL` | локальные переменные, объявленные до каретки и видимые в ней | `имя[:тип]` через пробел | да | да |
| `FIELD` | поля, события, константы текущего типа (в Go — поля получателя метода) | `имя:тип` через пробел | да | да |
| `PROPERTY` | свойства текущего типа | `имя:тип` через пробел | да | нет |
| `RECV` | тип получателя, когда каретка стоит после `.` / `?.` **или внутри имени члена** (`obj.Na⟨⟩`) [D1] | `ILogger<T>`; `type X` — статический доступ; `namespace X` / `package <import path>` | да | да |
| `MEMBER` | все доступные члены получателя (без фильтрации по набранному) | элементы через `; ` | да | да |
| `CALL` | перегрузки, применимые в текущей позиции списка аргументов | `сигнатура @индекс имя:тип` через ` \| ` | да | да (одна сигнатура) |

**Не входят в `v1.1`** [D4]: `METHOD` (методы текущего типа — 49 % токенов блока) и `TYPE` (контракты ближайших типов):
дорогие по токенам и сложные для плагинов. Вернём, если абляция покажет пользу.

### 5.2. Грамматика элементов [D5]

- `имя[:тип]`: тип необязателен (C# range-переменные, Go-локальные из неразрешённых модулей); «нет типа» лучше, чем `?`.
- Метод: `Имя(тип имя, …)->Результат`; C# всегда пишет результат (`->void`), Go без результатов опускает `->…`.
- Перегрузки сворачиваются по **имени** в один элемент с суффиксом ` +n` (n — сколько ещё перегрузок); выводится первая по
  каноническому порядку (`SymbolDisplay`-строка, ординально).
- Типы — только имя без пространства имён / пакета, даже при неоднозначности (`List<Order>`, `pgx.Row`, `*Order`).
- **Nullable (C#):** суффикс `?` выводится только у типов-значений из списка `int long short byte sbyte uint ulong ushort char
  bool float double decimal nint nuint DateTime DateTimeOffset TimeSpan Guid DateOnly TimeOnly` и у перечислений/структур,
  если плагин знает, что это `Nullable<T>`. У ссылочных типов `?` всегда снимается (обе стороны делают это одинаково).
- Тип из неразрешённой сборки (пакет, которого нет) печатается именем как в исходнике; `RECV`/`MEMBER` для него **не
  выводятся** [D3].
- Идентификаторы-ключевые слова экранируются как в языке (`@event`).

### 5.3. Порядок элементов внутри строки [D2]

- Сначала элементы, имя которых встречается как идентификатор в **видимом префиксе = тексте от `max(0, начало текущей строки −
  20 000)` до начала текущей строки** (UTF-16 символы; текст текущей строки не учитывается), затем остальные; внутри групп —
  как в экстракторе (собственные члены типа раньше унаследованных и методов расширения, затем по имени).
- Не более 24 элементов в строке (`contextMaxItemsPerLine`).

### 5.4. Бюджет блока и алгоритм обрезки [B4]

`contextFactsMaxTokens = 192` — включая `<|reserved_1|>` и `<|reserved_2|>`. Алгоритм (общий для обучения и плагина):

```
remaining = 192 - 2                                     # два спецтокена
for key in [EXPECT, RECV, CALL, ARG, LOCAL, RET, MEMBER, FIELD, PROPERTY]:   # приоритет
    items = first 24 items of key
    while items:
        cost = len(encode(key + " " + join(items, sep(key)))) + 1      # +1: "\n" между строками
        if cost <= remaining: break
        items.pop()                                     # удаляется последний элемент
    if items: admit(key, items); remaining -= cost
output admitted lines in the canonical order of 5.1, joined by "\n"
```

`cost` считается по токенам отдельной строки; итоговый блок кодируется целиком — расхождение длин на стыках строк ≤ 1 токена
на строку и в бюджет уже заложено (`+1`).

### 5.5. Обязательства плагина (иначе модель увидит не то, на чём училась)

- Факты считаются по документу **без недописанного хвоста текущей строки** (в обучении — снимок с удалённой целью); код ниже
  строки виден.
- Закрывающие символы, вставленные редактором после каретки на текущей строке (`)`, `]`, `}`, `"`), плагин **убирает из
  текста, по которому считает факты** [C5]: факты в обучающих данных посчитаны на снимке без них (пересчитать их с
  «вставленными» скобками для каждой позиции генератор не может).
- Переменная, объявляемая на текущей строке, в `LOCAL` не попадает.
- `MEMBER`/`CALL` — все доступные члены и все применимые перегрузки, без фильтрации по набранному префиксу.
- C#: факты только по типам **из исходников проекта и стандартной библиотеки (BCL)**; типы из пакетов NuGet — как
  неразрешённые: имя как в исходнике, без `RECV`/`MEMBER` [D3, решение пользователя (а)]. Так факты совпадают с обучающими
  данными (`adhoc`-семантика без пакетов).
- Плагин может подавать подмножество ключей (`contextKeys` в meta, раздел 9); обучение с выбросами (раздел 10) это покрывает.
- Бюджет времени на факты ≤ 20 мс; не уложился — блок не подаётся (или подаётся со следующего нажатия) [B2].

## 6. Бюджет промпта [B1]

Константы из meta (`.cml`), а не фактические длины:

```
prefixBudget = min(promptMaxPrefix, ctx - |header| - promptSuffixTokens - 3 - contextDepsMaxTokens - contextFactsMaxTokens)
```

`v1.1`: `ctx = 2000`, `promptSuffixTokens = 512`, `contextDepsMaxTokens = 48`, `contextFactsMaxTokens = 192`,
**`promptMaxPrefix = 896`** (по e18 укорочение префикса 1024 → 512 стоит < 1 п.п.). Требование:
`promptMaxPrefix + 256 ≤ ctx − |header| − promptSuffixTokens − 3 − depsMax − factsMax` для путей до 40 токенов — тогда
`stableTail` не упирается в `hardCap`, и окно префикса не сдвигается на каждом нажатии.

`stableTail` применяется к `encode(P)` **до** вставки блока; точка `I` ищется уже в обрезанном окне. Без контекста (модель
без ключей `context*` или плагин не подаёт контекст) — нынешние значения движка.

## 7. KV-кэш и стоимость [B2]

- `prefill` переиспользует общий префикс токенов. Порядок `суффикс → профиль → заголовок → префикс → факты → строка`.
- **Набор внутри строки:** префикс до `I` переиспользуется. Если блок не изменился — пересчитывается только набранное;
  если изменился — блок и строка (~100–250 токенов, по оценке ~15–45 мс для 31–100 M). Блок меняется, когда появляется `.`
  (`RECV`/`MEMBER`), `,` (индекс в `CALL`), `=`/`return`/`(` (`EXPECT`). Порядок элементов от текста текущей строки не
  зависит (5.3), поэтому лишних изменений нет.
- **Enter в конце строки** суффикс не меняет — дешёвый случай.
- **Переход на другую строку** меняет суффикс (он первый в SPM) → полный холодный prefill, теперь на ~240 токенов длиннее
  (+40 мс для 31 M, +65 мс для 50 M по `docs/PLUGIN_BASELINE.md`).
- Факты можно считать асинхронно и подставлять со следующего нажатия: обучение без блока это покрывает.

## 8. Режимы отказа (что модель видела в обучении)

| Ситуация в плагине | Что подаётся |
|---|---|
| ничего не посчитано | промпт без блока (и, возможно, без профиля) |
| тип получателя не определён / из пакета | без `RECV`/`MEMBER` |
| ожидаемый тип неоднозначен | без `EXPECT` |
| часть ключей не реализована | только реализованные ключи (`contextKeys`) |
| не уложились во время | без блока |

## 9. Метаданные модели [F1]

```
contextFormat=flc-context/v1.1
contextDepsToken=<|reserved_0|>
contextFactsTokens=<|reserved_1|>,<|reserved_2|>
contextDepsMaxTokens=48
contextFactsMaxTokens=192
contextMaxItemsPerLine=24
contextPrefixWindow=20000
contextKeys=RET,EXPECT,ARG,LOCAL,FIELD,PROPERTY,RECV,MEMBER,CALL
promptMaxPrefix=896
promptSuffixTokens=512
```

- Нет ключа `contextFormat` → модель старая, промпт как сейчас.
- Неизвестная **мажорная** версия `contextFormat` → промпт как сейчас (модель обучена и без контекста — это безопасно).
- Плагин проверяет, что `specialId` для всех названных токенов существует и `tokenizerSha256` совпадает.

## 10. Обучающие документы и смесь

### 10.1. Кареточный документ [C1]

По сэмплу датасета (позиция каретки, цель) и полному тексту файла из корпуса (без BOM, `\n`):

1. Текст редактора `E` = файл с удалённой целью (закрывающие символы не имитируются: см. 5.5 [C5]).
2. Лечёная граница `h = healedBoundary(E до каретки, E после каретки)` — **функцией движка**, тот же `healMode`.
3. `P` = `E[0:h]`, окно — `stableTail` с бюджетом раздела 6; `I` — раздел 2.
4. Суффикс — первые `promptSuffixTokens` токенов текста после конца текущей строки.
5. `mid = encode(текст от h до конца цели)` (набранный остаток + цель), затем `[<|endoftext|>]` — **как в нынешних
   SPM-документах `data.py`**, чтобы стоп был один и тот же.
6. Документ: SPM-порядок раздела 2 + `mid` + `[<|endoftext|>]`.
7. **Loss только на `mid` и `<|endoftext|>`** (маска −100 на всём остальном). Это изменение `data.py`: сейчас loss на всех
   позициях (`y = w[1:]`).

### 10.2. Смесь (стартовая, мерить)

| Доля | Документ |
|---|---|
| ~40 % | обычные документы корпуса (plain + FIM, как в рецепте движка), с профилем в ~80 % |
| ~60 % | кареточные документы 10.1 |
| из них ~25 % | без блока фактов |
| из них ~75 % | с блоком фактов, к которому применяется **одна** «порча» с вероятностью ~40 % [C3]: |
| | — выброс `MEMBER` при сохранённом `RECV`; — выброс методов расширения из `MEMBER`; — выброс случайных элементов из любой строки; — оставить только `RET`/`ARG`/`LOCAL`; — выброс случайного ключа целиком |
| ~80 % всех документов | с профилем (если не пустой) |

Сид фиксируется. Факты — конфигурация `semantic` датасетов (C#: с исправлениями `semantic-fix/`), профиль — `deps/`.
Документы из файлов, помеченных в `decontam/`, в оценку не идут.

### 10.3. Контроль [C4]

Вторая модель на **той же смеси**, где профиль и блок всегда выброшены. Сравнение парное, ≥ 10 000 позиций, бутстреп;
отдельно — позиции, где ответ содержит идентификатор, которого нет ни в префиксе, ни в суффиксе (только там факты могут
помочь; ~5 % позиций).

## 11. Эталоны для тестов плагина [F2]

- `fixtures/context/golden-prompt-{csharp,go}.jsonl`: даны файл, каретка, профиль и факты → проверяются **побайтные id
  токенов промпта**, допуск 0. Обязательные случаи: одна и две пустые строки над текущей, пустая строка с пробелами, CRLF
  в исходном файле, первая строка файла, BOM, каретка в отступе, длинная строка, обрезка блока по бюджету, профиль на пределе

## 12. Проверка ценности до доработки плагинов

1. Прокси-модель на смеси 10.2 и контрольная 10.3.
2. Оценка в трёх режимах на одних позициях: без контекста, только профиль, профиль + факты; на чистом наборе `eval-fresh`
   (без файлов из `eval-fresh/decontam/`) и на test.
3. Разбивка по типу позиции.
4. В плагины — при приросте ≥ 1–2 п.п. в целом или заметно больше после `.` / в аргументах, при значимости по бутстрепу.

## 13. Решения и открытые вопросы

Решено (2026-10-09): C# факты без NuGet (вариант (а)); `TYPE`/`METHOD` не входят в `v1.1`; профиль перед `<|file_sep|>`, без
слова `DEPS`; `promptMaxPrefix 896`; текст без BOM, `\n`; терминатор `<|endoftext|>`; Go `PKG` не вводится [G3].

Открыто: бюджет фактов 192 против 256; вклад профиля в тестовом и рабочем коде отдельно [G4]; асинхронные факты в плагине.
